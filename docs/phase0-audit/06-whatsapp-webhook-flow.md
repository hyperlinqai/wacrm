# WhatsApp Integration — Current-State Architecture Audit

## Overview / Architecture

wacrm is a single Next.js app that talks to Meta's WhatsApp Cloud API directly (no BSP middleware). All WhatsApp plumbing lives under `src/app/api/whatsapp/*` (routes) and `src/lib/whatsapp/*` (shared logic). Tenancy today is **account-based, not per-number multi-tenant SaaS**: the schema was migrated from `user_id`-scoped rows (migration `001_initial_schema.sql`) to `account_id`-scoped rows with account membership/roles (migration `017_account_sharing.sql`), and each `accounts` row has exactly one `whatsapp_config` row (`whatsapp_config_account_id_key UNIQUE(account_id)`, migration `017_account_sharing.sql` line 326). Each WhatsApp Business phone number (`phone_number_id`) is globally unique across the whole app instance (`whatsapp_config_phone_number_id_key UNIQUE(phone_number_id)`, migration `013_whatsapp_config_phone_number_id_unique.sql`) — i.e. today's tenancy key for inbound routing is `phone_number_id → whatsapp_config.account_id`.

Two secrets are **global to the app instance, not per-tenant**:
- `META_APP_SECRET` — one Meta App used to verify every account's inbound webhook HMAC (`src/lib/whatsapp/webhook-signature.ts`).
- `ENCRYPTION_KEY` — one AES-256-GCM key used to encrypt every account's `whatsapp_config.access_token` / `verify_token` (`src/lib/whatsapp/encryption.ts`).

Both are declared in `.env.local.example` (lines 23–33) as required, single, instance-wide env vars.

## Webhook Verification (GET handshake)

`src/app/api/whatsapp/webhook/route.ts`, `export async function GET(request)`:
1. Reads `hub.mode`, `hub.challenge`, `hub.verify_token` query params; 400s if `mode !== 'subscribe'` or challenge/token missing.
2. Loads **all** `whatsapp_config` rows (`select('id, verify_token')` with no account filter) and linearly decrypts each row's `verify_token`, comparing it to the incoming `hub.verify_token` until a match is found (lines 112–140). This is O(n) over every tenant's config on every verification call — fine at small scale, but note for multi-tenancy: there's exactly one webhook URL/endpoint for the whole instance, and account resolution at verify time is done by brute-force decrypt-and-compare across all tenants' stored tokens.
3. On match, if the matched row's `verify_token` was still in legacy CBC format, it's opportunistically re-encrypted to GCM (fire-and-forget, lines 142–158).
4. Returns `challenge` as `text/plain`, 200. No match → 403 `{ error: 'Verification token mismatch' }`.

## Webhook Signature Verification

`src/lib/whatsapp/webhook-signature.ts`, `verifyMetaWebhookSignature(rawBody, signatureHeader)`:
- Fails **closed**: if `META_APP_SECRET` is unset, every request is rejected (logs an error) — no silent fallthrough.
- Requires header `x-hub-signature-256: sha256=<hex>`.
- Computes `HMAC-SHA256(secret, rawBody)` and compares to the header via `crypto.timingSafeEqual` (constant-time), after a length check to avoid the throw `timingSafeEqual` raises on mismatched buffer lengths.
- Called in `POST` (`webhook/route.ts` lines 180–192) against `request.text()` (the **raw** body, read before any JSON parsing, specifically to preserve the exact bytes Meta signed) — `request.json()` is deliberately avoided because re-serializing would break the signature match.
- On failure: `401` (not `200`) so Meta's delivery dashboard surfaces the failure instead of Meta silently believing delivery succeeded.

Multi-tenancy implication: **one shared `META_APP_SECRET` for the whole instance** means signature verification does not (and cannot, as currently coded) distinguish which tenant's Meta App sent the payload — it only proves "this came from *a* Meta App using this instance's configured secret." Per-account Meta Apps would need per-account secrets and a way to route which secret to try (there's no field carrying that hint pre-verification).

## Inbound Message Flow (webhook `POST`)

`src/app/api/whatsapp/webhook/route.ts`, `POST(request)`:

1. **Receive**: read raw body + signature header; verify signature (see above); reject with 401 on failure.
2. **Parse**: `JSON.parse(rawBody)`; 400 on invalid JSON.
3. **Ack fast, process async**: the actual processing is wrapped in Next's `after()` callback (not a detached promise) so the route can return `{status:'received'}` 200 immediately while `after()` keeps the serverless function alive until `processWebhook(body)` finishes — a fire-and-forget promise was previously found to drop messages on Vercel because the function froze/terminated right after the response (documented as issue #301 in code comments). `maxDuration = 60` is set to give this headroom.
4. **`processWebhook(body)`** iterates `body.entry[].changes[]`:
   - Template-lifecycle events (`isTemplateWebhookField(change.field)`) are routed to `handleTemplateWebhookChange` (`src/lib/whatsapp/template-webhook.ts`) and skip the messaging branches.
   - `value.statuses[]` → `handleStatusUpdate(status)` per status (see Status/Read-Receipt Handling below).
   - `value.messages` + `value.contacts` → resolve tenancy, then loop messages.
5. **Resolve account / whatsapp_config** (lines 256–293): `phoneNumberId = value.metadata.phone_number_id`; query `whatsapp_config` `.eq('phone_number_id', phoneNumberId)` (no `.single()` — explicitly avoided so 0-row and ≥2-row cases can be distinguished and logged separately).
   - 0 rows → `console.error`, message dropped.
   - ≥2 rows → `console.error` with all `account_id`/`user_id` owners logged, message **dropped entirely** (shouldn't happen post-migration-013's UNIQUE constraint, but code defends against a pre-constraint stale row or a race).
   - Exactly 1 row → this is the **sole point where inbound tenancy is decided**: `config.account_id` becomes the account every downstream row is stamped with, `config.user_id` becomes the audit "sender of record" for NOT-NULL FK columns, `config.access_token` (decrypted) is used for Meta media/API calls, `config.mirror_inbound_media !== false` gates the media mirror.
6. **`processMessage(message, contact, accountId, configOwnerUserId, accessToken, mirrorMedia)`** per message:
   - `findOrCreateContact` — dedupes by phone within the account via `findExistingContact` (`src/lib/contacts/dedupe.ts`), pre-filtered by last-8-digits then strict-matched in JS; updates `name` if changed; on a unique-violation race (migration 022's phone-dedup index) re-resolves rather than erroring.
   - `findOrCreateConversation` — one conversation per `(account_id, contact_id)`, oldest-first `.limit(1)` lookup (deliberately not `.single()`, to converge duplicates instead of spawning new ones — issue #363); same unique-violation race handling (migration 036's dedup index).
   - Emits `conversation.created` webhook event (`dispatchWebhookEvent`) if the conversation was just created — **before** the reaction short-circuit, so a thread opened purely by a reaction still fires the event.
   - **Reactions** (`message.type === 'reaction'`) short-circuit into `handleReaction` and return — never inserted into `messages`, never bump unread/last-message.
   - `parseMessageContent` — type-switches on `text/image/video/document/audio/sticker/location/reaction/interactive/button`; for media types calls `getMediaUrl` (Meta) then `mirrorInboundMedia` if enabled (see Inbound Media Handling).
   - Swipe-reply context (`message.context.id`) resolved to an internal message UUID via `lookupInternalIdByMetaId`, scoped to the conversation; missing parent → stored as `null`, not an error.
   - **Idempotent insert into `messages`**: `.upsert(..., { onConflict: 'conversation_id,message_id', ignoreDuplicates: true })` relying on the unique index added in migration `037_webhook_broadcast_reliability.sql` (`idx_messages_conversation_message_id` on `(conversation_id, message_id)`) — this is the single idempotency boundary (issue #367); a Meta retry replay returns 0 inserted rows and the function returns early, skipping unread bump, flows, automations, AI reply, and webhook dispatch.
   - `bump_conversation_on_inbound` RPC (DB-side atomic increment, migration 037, `SECURITY DEFINER`, granted only to `service_role`) updates `unread_count`, `last_message_text`, `last_message_at` atomically to avoid the lost-update race under concurrent inbound deliveries (issue #369).
   - `reopenClosedConversation` (`src/lib/conversations/reopen.ts`) re-opens a closed thread on a new customer message (issue #409).
   - `flagBroadcastReplyIfAny(accountId, contactId)` — best-effort, marks the most recent unreplied `broadcast_recipients` row `replied` if this contact was a broadcast target (account-scoped join `broadcasts!inner(account_id)`).
   - **Flow engine dispatch**: `dispatchInboundToFlows` (`src/lib/flows/engine.ts`) is awaited (not fire-and-forget) so its `consumed` result gates automation triggers; if consumed, the content-level automation triggers (`new_message_received`, `keyword_match`) are suppressed but relationship-level triggers (`new_contact_created`, `first_inbound_message`) still fire.
   - **Automations**: `runAutomationsForTrigger` (`src/lib/automations/engine.ts`) called per triggered type (`new_contact_created`, `first_inbound_message`, `new_message_received`, `keyword_match`, `interactive_reply`), awaited with a `.catch` guard so a failure in one trigger type doesn't skip the rest.
   - **AI auto-reply**: `dispatchInboundToAiReply` (`src/lib/ai/auto-reply.ts`) runs only for plain-text inbound *not* consumed by the flow engine and *not* an interactive reply, and only when the account has it enabled (its own eligibility gate). Awaited inside `after()`.
   - **Public webhook fan-out**: `dispatchWebhookEvent(supabaseAdmin(), accountId, 'message.received', {...})` (`src/lib/webhooks/deliver.ts`) — early-exits if the account has no configured endpoint (migration `028_webhook_endpoints.sql`).

## Inbound Media Handling

`src/lib/whatsapp/mirror-inbound-media.ts`, invoked from `parseMessageContent`'s `verifyAndBuildUrl` closure in `webhook/route.ts`:
- For each media message type, `getMediaUrl({ mediaId, accessToken })` (`src/lib/whatsapp/meta-api.ts`) resolves Meta's short-lived CDN URL + `mimeType`/`fileSize`.
- If `mirror` is enabled (`whatsapp_config.mirror_inbound_media !== false`, default `TRUE`, added by migration `039_inbound_media_mirror.sql`), `mirrorInboundMedia(...)` downloads the bytes and uploads them into the shared `chat-media` Storage bucket at `account-<accountId>/inbound/<mediaId>-<name>.<ext>` (`buildMediaPath(accountId, objectName, null, 'inbound')`), returning a durable public URL. This exists because Meta deletes media ~30 days after receipt (issue #466); previously the app stored only `/api/whatsapp/media/<mediaId>` proxy pointers that silently expired.
- Size guards: skips before download if Meta's advertised `fileSize > MEDIA_MAX_BYTES` (bucket cap 16 MB, migration 039), and re-checks after download since Meta's `file_size` is advisory.
- MIME normalization strips parameters (e.g. `audio/ogg; codecs=opus` → `audio/ogg`) and falls back through Meta's metadata MIME → downloaded `Content-Type` → `application/octet-stream`.
- Entirely best-effort: any failure (oversized, disallowed MIME, storage outage) returns `null` and the webhook falls back to the `/api/whatsapp/media/<mediaId>` proxy route — the mirror never throws, so a storage outage can't cause Meta webhook retries.
- Object path is deterministic (keyed by Meta's `mediaId`, `upsert: true`), so a Meta redelivery re-writes the same object rather than duplicating it.
- `messages.media_type` (added by migration 039) persists Meta's MIME type so the download/display path doesn't have to guess an extension from raw bytes.
- Tenancy: `mirrorInboundMedia` is called with `{ accountId }` from `config.account_id` — the media object path is account-scoped (`account-<accountId>/inbound/...`), consistent with the `chat-media` bucket's RLS policies (first path segment match, migration 023) — but note the webhook mirror call runs under the **service-role** Storage client, bypassing RLS entirely (comment in `mirror-inbound-media.ts`: "RLS is bypassed, MIME/size limits are not").
- The proxy route `src/app/api/whatsapp/media/[mediaId]/route.ts` (`GET`) re-fetches from Meta on every call, using the requesting user's own account's `whatsapp_config` (resolved via `profiles.account_id`) — i.e. it re-derives the token from the *caller's* account, not from any account embedded in the mediaId, so it only works correctly for a user viewing their own account's media (see Multi-Tenancy Notes).

## Status / Read-Receipt Handling

`handleStatusUpdate(status)` in `webhook/route.ts`, invoked per `value.statuses[]` entry (not gated by account resolution — runs before the messages branch and does its own lookups):
1. **Mirror onto `messages`**: `UPDATE messages SET status = status.status WHERE message_id = status.id` — no `.select()`/no assumption of a single row, since `message_id` (Meta's wamid) is **not globally unique** across phone numbers (migration 009 comment) — it can legitimately match rows in multiple accounts/conversations. This update runs across **all** matching rows regardless of account, purely on `message_id` match — a cross-tenant collision here (extremely unlikely wamid namespace collision, but noted) could theoretically bleed a status update across accounts, since there's no account filter.
2. **Mirror onto `broadcast_recipients`** via `whatsapp_message_id` (migration 003 column): fetches the recipient row, then applies `isValidStatusTransition` — a forward-only status ladder (`pending → sent → delivered → read → replied`, with `failed` only valid as a terminal branch from `pending`/`sent`) so a Meta webhook replay or out-of-order delivery can never regress a recipient's state. Updates `sent_at`/`delivered_at`/`read_at` timestamps accordingly. The DB aggregate trigger (migrations 003/005) re-derives the parent `broadcasts` sent/delivered/read/failed counts automatically from this table — never written directly by app code here.
3. **Public webhook fan-out**: resolves `conversation_id → conversations(account_id)` for the matching message row (bounded `.limit(1).maybeSingle()`, again purely on `message_id`), then `dispatchWebhookEvent(..., 'message.status_updated', {...})` for that resolved account. Runs last deliberately so a slow subscriber endpoint can't delay the broadcast-recipient mirror above.

**Reactions** (separate from status): handled by `handleReaction` in `processMessage` — not new `messages` rows; upserted/deleted in `message_reactions` keyed by `(message_id, actor_type, actor_id)` (unique constraint), resolving the target's Meta id → internal id via `lookupInternalIdByMetaId` scoped to the conversation. A missing target parent is logged and skipped (still 200s to Meta).

## Outbound Send Flow

Dashboard route: `src/app/api/whatsapp/send/route.ts`, `POST`. Public API reuses the same core (`sendMessageToConversation`).
1. **Auth + role**: `requireRole('agent')` — explicitly stronger than resolving `account_id` off the profile (any `viewer` could do that), because the send core calls Meta **before** persisting; RLS can't retroactively un-send a message that already left the building even if the DB write is blocked.
2. **Rate limit**: `checkRateLimit('send:${userId}', RATE_LIMITS.send)` — 60/min per user, **in-memory, single-process** (see `src/lib/rate-limit.ts` — explicitly documented as not surviving horizontal scale/multiple serverless instances without a Redis/Upstash swap).
3. **Validate params**: `validateSendMessageParams` (`src/lib/whatsapp/send-message.ts`) checks message-type-specific required fields (text needs `content_text`, template needs `template_name`, media needs `media_url`, interactive payload validated against Meta limits, caption ≤1024 chars) — done **before** any conversation is found-or-created so a bad payload 400s without leaving an orphan empty conversation.
4. **Resolve conversation**: either an existing `conversation_id` (account-scoped lookup) or find-or-create from `contact_id` (mirrors the webhook's find-or-create convention).
5. **`sendMessageToConversation(db, accountId, params)`** (`src/lib/whatsapp/send-message.ts`) — the shared core also used by `/api/v1/messages`:
   - Loads conversation + embedded contact, account-scoped (`.eq('account_id', accountId)`).
   - Loads `whatsapp_config` account-scoped (`.eq('account_id', accountId).single()`), decrypts `access_token`; self-heals legacy CBC ciphertext to GCM fire-and-forget.
   - Resolves `reply_to_message_id` → Meta `message_id`, but only if the parent belongs to the **same conversation** (prevents quoting messages the caller can't see by guessing UUIDs).
   - For `template` type, resolves the local `message_templates` row via `resolveTemplateRow` (tolerant of `en`/`en_US` language variants).
   - **Sends via Meta** using `phoneNumberId: config.phone_number_id` + decrypted `accessToken`, dispatching to `sendTextMessage` / `sendTemplateMessage` / `sendMediaMessage` / `sendInteractiveButtons` / `sendInteractiveList` (`src/lib/whatsapp/meta-api.ts`, Graph API `v21.0`, `POST /{phoneNumberId}/messages`).
   - **Phone-variant retry**: `phoneVariants(sanitizedPhone)` tried in order; on a "recipient not in allowed list" Meta error (`isRecipientNotAllowedError`) the next variant is tried; on success the contact's stored phone is auto-corrected to the working variant.
   - **Persists** the sent message into `messages` (`sender_type: 'agent'`, `status: 'sent'`, `message_id: waMessageId`); updates `conversations.last_message_text`/`last_message_at`.
   - **Pauses active Flow runs** for the contact (`flow_runs.status = 'paused_by_agent'`) — an agent manually replying is treated as the strongest signal that the bot should yield, best-effort/non-blocking.
   - Throws a typed `SendMessageError { code, message, status }` on any failure; both callers (dashboard route, public API) map this to their own response shape.

## Template Management

- **Sync from Meta**: `src/app/api/whatsapp/templates/sync/route.ts`, `POST`, `requireRole('admin')`. Paginates Meta's `GET /{waba_id}/message_templates` (page cap 20 × 100 = 2000 templates), normalizes category/quality-score/buttons/header type, and upserts into `message_templates` keyed by `(account_id, name, language)`. Local-only templates (no Meta counterpart) are never deleted — left visible for drift detection.
- **Submit new template**: `src/app/api/whatsapp/templates/submit/route.ts`, `POST`, `requireRole('admin')` (explicitly hardened — pushing a template to Meta is an external side effect RLS can't undo, so a viewer/agent role check alone would be insufficient after the fact). Rejects `Authentication` category (out of scope; must use Meta's own UI + Sync). Validates payload (`validateTemplatePayload`), optionally uploads an IMAGE header via Meta's Resumable Upload API (`ensureImageHeaderHandle`, requires `META_APP_ID`), then `submitMessageTemplate` (`POST /{waba_id}/message_templates`). Supports a `WHATSAPP_TEMPLATES_DRY_RUN=true` mode that synthesizes a `dry-run-<uuid>` id and skips the Meta call entirely (for CI/local dev without a real WABA). Upserts locally on `(user_id, name, language)` — flagged in a `TODO` comment as still user-scoped rather than `(account_id, name, language)`, meaning **two teammates on the same account could currently shadow each other's identically-named template** (a known, un-fixed multi-tenancy-adjacent bug even pre-SaaS-conversion).
- **Template webhook events** (status/quality/component changes from Meta) are routed by `webhook/route.ts` through `isTemplateWebhookField(change.field)` → `handleTemplateWebhookChange` (`src/lib/whatsapp/template-webhook.ts`), separate from the messaging change branch.
- **Template send building**: `src/lib/whatsapp/template-send-builder.ts` + `template-components.ts` + `template-body.ts` assemble Meta's component JSON (header/body/button params) from either legacy positional `params` or structured `messageParams`.

## Broadcast Flow (including resume/reliability)

Two parallel broadcast code paths exist:

**A. Dashboard-driven broadcast** — `src/app/api/whatsapp/broadcast/route.ts`, `POST`, `requireRole('agent')`. Writes **nothing** to the DB itself (no `broadcasts`/`broadcast_recipients` rows) — it's a stateless fan-out loop that reads config+template once, then per-recipient sanitizes phone, retries phone variants on Meta rejection, and calls `sendTemplateMessage` directly, returning a results array. Rate-limited via `broadcast:${userId}` (60/min, same in-memory limiter caveat). This is the "wizard" path referenced in the resume-route comments — the actual campaign wizard UI apparently persists its own `broadcasts`/`broadcast_recipients` rows client-side per batch (not shown in this route) and drives the send loop from the browser tab.

**B. Public-API / resumable broadcast core** — `src/lib/whatsapp/broadcast-core.ts`:
- `createBroadcast(db, accountId, auditUserId, params)`: validates (max 1000 recipients/request), resolves each recipient to a contact (`findOrCreateContact`), dedupes by resolved `contactId`, then calls the `create_broadcast_with_recipients` **Postgres function** (migration 038's 8-arg version, superseding migration 037's 7-arg version) to insert the parent `broadcasts` row and all `broadcast_recipients` rows **atomically in one transaction** — fixing issue #370, where a recipient-insert failure after a parent insert had succeeded left an orphaned `sending` broadcast with zero recipients. Per-recipient `template_params` are frozen into the `broadcast_recipients.template_params` JSONB column (migration `038_broadcast_resume.sql`) at plan time, so a later resume replays exactly what was originally intended rather than re-resolving against (possibly since-edited) contact data.
- `deliverBroadcast(db, plan)`: sequential per-recipient send with phone-variant retry, stamping each `broadcast_recipients` row `sent`/`failed`; aggregate status counts (`sent_count`/`delivered_count`/etc.) are DB-trigger-owned (migrations 003/005), never written by app code directly, to avoid races with the webhook's status mirror.
- `finalizeBroadcastStatus`: flips the parent `broadcasts.status` out of `sending` once no `pending` recipient rows remain, based on the actual recipient rows rather than a per-pass counter (so a partial resume of an 800/1000-already-sent campaign doesn't get misreported as `failed`).

**Resume/retry**: `src/app/api/whatsapp/broadcast/[id]/resume/route.ts`, `POST`, `requireRole('agent')`, `maxDuration = 300`. Fixes issue #472 (browser-tab-driven sends stranding recipients if the tab closes mid-campaign):
- **Mutex via `claimBroadcastDelivery`** (`src/lib/whatsapp/broadcast-resume.ts`): one conditional `UPDATE broadcasts SET delivery_locked_at = now() WHERE id=... AND (delivery_locked_at IS NULL OR delivery_locked_at < staleCutoff)` — atomic single-statement claim, so two concurrent "Resume" clicks can't both build a send plan and double-message everyone (a WhatsApp message can't be recalled). Stale-lock window: 30 minutes (`DELIVERY_LOCK_STALE_MS`), recovering from a crashed pass.
- **`planBroadcastResume`**: loads recipient rows in the requested `scope` (`pending` | `failed` | `all`), stamps unsendable rows (contact has no valid E.164 phone) `failed` up front so they stop blocking terminal status, caps the plan at `RESUME_MAX_PER_REQUEST = 1000`, and rebuilds the `BroadcastPlan` from the **frozen** `template_params` on each recipient row (not re-resolved from current contact data).
- Delivery runs inside `after()` using a **service-role** client (`supabaseAdmin()`), releasing the lock in a `finally`; on a thrown error it still calls `finalizeBroadcastStatus` before releasing, so nothing is left stranded mid-flight.
- Route responds `202` immediately with `{ resuming, remaining, unsendable }` so the UI can poll and offer "Resume again" if the backlog exceeded one pass's cap.

## Per-Account WhatsApp Config & Token Security

- **Table**: `whatsapp_config`, originally `user_id`-scoped with `UNIQUE(user_id)` (migration 001), migrated to `account_id`-scoped with `UNIQUE(account_id)` (migration 017 — `whatsapp_config_account_id_key`) plus the cross-account `UNIQUE(phone_number_id)` constraint (migration 013). So **today**: one WhatsApp number per account, and one config row per account — this is the exact seam that would need to change for true multi-tenant SaaS (currently enforced at the DB level as a hard 1:1, not a 1:many).
- **RLS**: `whatsapp_config_select` — any account member (`is_account_member(account_id)`); insert/update/delete require `is_account_member(account_id, 'admin')` (migration 017, lines 419–424).
- **Save flow**: `src/app/api/whatsapp/config/route.ts`, `POST` — requires session auth, resolves `accountId` from `profiles.account_id`.
  1. **Cross-account collision check**: queries via the **service-role** admin client (bypassing RLS deliberately, since a normal user's RLS-scoped client can't see other accounts' rows) whether `phone_number_id` is already claimed by a different `account_id`; 409s if so. Comment explicitly frames this as "wacrm is single-tenant-per-WhatsApp-number by design" (issue #136) — inbound webhook routing depends on this being enforced.
  2. **Verifies credentials with Meta** (`verifyPhoneNumber`) *before* persisting anything.
  3. **Encrypts** `access_token` and `verify_token` via `encrypt()` (AES-256-GCM, `ENCRYPTION_KEY` env var, 64 hex chars / 32 bytes) — `src/lib/whatsapp/encryption.ts`. Format: `<iv-hex>:<ciphertext-hex>:<authTag-hex>`; legacy CBC format (`<iv-hex>:<ciphertext-hex>`, 2-part) is decrypt-only, auto-detected by counting colon-delimited parts, and opportunistically upgraded to GCM on read paths across the codebase (webhook GET, send-message core).
  4. **Registration**: `registerPhoneNumber` (Meta's `/register` + 6-digit PIN) is attempted on first save or whenever a fresh PIN is supplied; skipped (not failed) when no PIN is given, since Meta test numbers expose no 2FA PIN (issue #242) — the row is still saved as `connected` with `registered_at: null` and the UI shows a "Not registered" banner.
  5. **WABA app subscription**: `subscribeWabaToApp` — idempotent, called on every save if `waba_id` present; failure is non-fatal (logged, not blocking).
  6. Row upserted with `status: 'connected'|'disconnected'`, `registered_at`, `subscribed_apps_at`, `last_registration_error`.
- **`GET /api/whatsapp/config`**: health check — decrypts the token and calls `verifyPhoneNumber` against Meta; distinguishes `no_config` / `token_corrupted` (decryption failure — surfaces `needs_reset: true`, meaning ENCRYPTION_KEY mismatch across environments) / `meta_api_error`.
- **`GET /api/whatsapp/config/verify-registration`** (`src/app/api/whatsapp/config/verify-registration/route.ts`): three independent live checks against Meta — phone metadata reachable, WABA has our app in `subscribed_apps`, and `registered_at` is locally set — combined into a single `live` boolean, specifically built to diagnose "UI says Connected but Meta isn't delivering events" (the original multi-number bug, issue #136).
- **DELETE**: resets/clears the account's config row (used to recover from an undecryptable token after an `ENCRYPTION_KEY` change).
- **Token security summary**: tokens are encrypted at rest with a **single, instance-wide** symmetric key (not per-tenant, not envelope-encrypted per account, no KMS/HSM involved) using authenticated encryption (GCM) so tampering fails decrypt hard rather than silently corrupting. Decrypted tokens are held only in-process per request, never logged.

## Multi-Tenancy Notes / Risks for the SaaS Conversion

1. **Hard 1:1 account↔number today.** `whatsapp_config` is `UNIQUE(account_id)` *and* `phone_number_id` is `UNIQUE` instance-wide (migrations 013, 017). This is by design for the current single-tenant/self-hosted model and must be relaxed (or explicitly kept, if "one number per tenant" is an acceptable SaaS constraint) before onboarding many accounts on one deployment — but as currently coded, two different SaaS customers **cannot** already collide, because the unique constraint plus the `/config POST` pre-check (`route.ts` lines 210–233) both reject a duplicate `phone_number_id` claim.
2. **Correct multi-account webhook routing exists.** The single shared webhook endpoint (one Meta App, one webhook URL) already resolves inbound traffic to the right tenant purely by `phone_number_id → whatsapp_config.account_id` (`webhook/route.ts` lines 256–293), and defends against the ambiguous case (0 or ≥2 matching configs) by dropping the message and logging loudly rather than guessing. This part of the architecture is already SaaS-shaped — it just currently guarantees the "≥2 rows" case never legitimately happens via the DB constraint.
3. **Global secrets, not per-tenant.** `META_APP_SECRET` (webhook HMAC) and `ENCRYPTION_KEY` (token cipher) are single environment-wide values. For true multi-tenant SaaS with tenant-specific Meta Apps (e.g. Embedded Signup / Tech Provider flow where each customer's WABA is under the *platform's* single Meta App — the common WhatsApp BSP pattern), a single shared secret set is actually fine and is what Meta's own multi-WABA Tech Provider model expects (one App Secret verifies webhooks for every WABA subscribed to that one App). It would only become a problem if the SaaS design wanted per-tenant Meta Apps.
4. **Status-update mirror has no account filter.** `handleStatusUpdate`'s first step (`UPDATE messages SET status=... WHERE message_id=status.id`) matches purely on Meta's `message_id`, which the code's own comments say is **not globally unique across phone numbers** (migration 009). At larger multi-tenant scale this is a theoretical cross-tenant status leak vector (extremely low probability given wamid's structure, but worth flagging in the audit) — the broadcast-recipient mirror and the public-webhook-fan-out step that follow it do scope by `whatsapp_message_id` / resolved `account_id` respectively, but the raw `messages` mirror does not.
5. **In-memory rate limiting won't survive horizontal scale.** `src/lib/rate-limit.ts` is explicitly documented as a single-process `Map` — fine for "one VPS," but converting to SaaS almost certainly means multiple app instances/regions, which silently defeats every rate limit (`send`, `broadcast`, `react`) across all tenants. Needs Redis/Upstash before scale-out.
6. **Template upsert conflict key is still `user_id`-scoped**, not `account_id`-scoped (`templates/submit/route.ts`, `upsertTemplateRow`, flagged with a `TODO(account-sharing)` comment in the code itself) — a pre-existing multi-*user* bug (two teammates in one account can shadow each other's template) that would need fixing regardless of SaaS conversion, but is more likely to matter as account sizes grow.
7. **Media proxy route derives tenancy from the viewer's own session**, not from any tenant marker on the `mediaId` itself (`media/[mediaId]/route.ts` — looks up the *caller's* `profiles.account_id` → that account's `whatsapp_config`, then calls Meta with that account's token for whatever `mediaId` was requested in the URL). This works today because a user only ever links to media belonging to their own account's conversations, but it means the route has **no authorization check that the requested `mediaId` actually belongs to the caller's account** — a user could pass an arbitrary Meta `mediaId` and — if the *caller's own* WhatsApp access token happens to have visibility (unlikely across separate Meta Apps/WABAs, but not something the code itself checks) — potentially fetch media outside their tenant. Worth a closer security pass before SaaS launch; the mirrored inbound media (durable `chat-media` URLs) sidesteps this by embedding `account_id` in the storage path and relying on bucket path-based RLS, but the fallback proxy path does not have an equivalent per-mediaId ownership check.
8. **Audit user (`user_id`) on inbound-created rows is always the WhatsApp config owner**, not "whoever is on duty" — stable but arbitrary; fine within one account, doesn't change under SaaS.
9. **Broadcast's dashboard-driven path (`/api/whatsapp/broadcast`) persists nothing and has no resumability** — only the public-API path (`broadcast-core.ts` + resume route) has the reliability/resume machinery. If the SaaS product surfaces broadcasts as a core paid feature, the dashboard wizard's client-driven, non-persisted fan-out is the weaker of the two implementations and would benefit from being unified onto the resumable core.
